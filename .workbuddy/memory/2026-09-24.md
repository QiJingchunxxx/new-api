## 第二轮：改成「共享号池」+ 隐藏 Key 与内部信息 + FAQ 页 + 钱包每日额度

### 关键设计决策：用 new-api 原生多 Key 轮询做共享号池
- 放弃「一个贡献 Key 一个渠道」，改为**每个供应商一个号池渠道**：`ChannelInfo.IsMultiKey=true`、
  `MultiKeyMode=constant.MultiKeyModePolling`、Key 用 `\n` 拼接、`AutoBan=1`。
- 轮询：`Channel.GetNextEnabledKey()` 在 polling 模式下按 `MultiKeyPollingIndex` 顺序取 Key。
- **无痕切换的前提**：`service.DisableChannel` 只在 `channelError.AutoBan` 为 true 时才生效，
  且多 Key 渠道下 `handlerMultiKeyUpdate` 只禁用出错的**那一个 Key 索引**（`MultiKeyStatusList`），
  请求随即重试到下一个 Key；因此号池渠道必须 `AutoBan=1`（第一轮写成 0 是错的，已修）。
- **另一个硬前提**：`common.RetryTimes` 默认是 0 → 失败根本不重试，用户会直接看到错误。
  已做成管理端可见告警 + 一键把 `RetryTimes` 设为 2（`PUT /api/option/`），并在号池卡片里提示。
- 号池写入走 `model.SaveContributedPoolChannel`：**刻意不用** `Channel.Update` / `UpdateChannelStatus`，
  因为那两个入口会给管理员推「渠道已禁用/已启用」通知，Key 频繁进出会刷屏；改为 `Select(...).Updates(Channel{...})`
  （保证零值也写入、`channel_info` 走 schema 序列化）+ `UpdateAbilities` + `CacheUpdateChannel`。
- 变更后调用 `model.InitChannelCache()`，否则新号池要等下一次 `SyncChannelCache` 才可调度。
- 复检任务结束后 `SyncContributedPools(..., heal=true)`：清掉失效 Key，并把请求链路临时禁用的 Key 静默放回。
  Key 列表变化时索引会错位，必须整体丢弃 `MultiKeyStatusList` 重来。

## Docker 部署答疑（用户反馈"服务器上改的东西都不见了"）
- 结论：不是被覆盖，而是**官方镜像里本来就没有源码**。`Dockerfile` 三段构建（bun 出 web/dist → golang 把 dist 一起编译成单个 `/new-api` → debian 只 COPY 这个二进制），
  而 `docker-compose.yml` 用的是 `image: calciumion/new-api:latest`（远程镜像），本地源码改动完全不参与。
- 会保留：`./data`、`./logs`、`pg_data/mysql_data` 卷，以及**后台 UI 里改的配置项（存在数据库 options 表）**。
- 会丢：容器内的任何文件改动、宿主机改了源码但没重建镜像的部分。
- 自定义改动上线方式：compose 加 `build: {context: ., dockerfile: Dockerfile}` 并 `image: my-new-api:custom`，然后 `docker compose build && up -d`；
  或本地/CI 构建后推自己的 registry。`docker-compose.dev.yml` 是本地开发用的（build + image: new-api-dev:local，前端走 5173 dev server）。
- 注意：`web/dist` 是 gitignore 的，`go:embed` 必须先生成它；Dockerfile 会自动构建前端，但直接在宿主机 `go build` 前必须先 `cd web && bun run build`。

### 从官方镜像切到自建镜像的迁移步骤（已告知用户）
- 不动数据库的最小操作：`docker compose rm -sf new-api` → `docker image rm calciumion/new-api:latest` → `docker compose up -d --build new-api`。
- **绝对不能加 `-v`**（`docker compose down -v` 会删掉 pg_data 等卷 = 删库）。
- 验证新代码是否生效的特有接口：`curl -s localhost:3000/api/home_landing`（官方镜像返回 404，本分支返回 JSON）。
- `deploy.sh` 已支持 `--clean`（删容器 + 删所有 `calciumion/new-api:*` 镜像 + `image prune -f`，并在检测到 watchtower 时告警）
  与 `--pull`，可组合；末尾做镜像自检（比对 `docker inspect new-api --format '{{.Config.Image}}'`）。
  已用打桩的假 docker 跑通全部分支（含负向：无容器/无镜像/跑的是官方镜像/非法参数 exit 1）。
- **执行顺序已改为「先 build → 再 clean → 最后 up」**：原顺序会在构建的十几分钟里删掉运行中的容器，造成不必要的停机。
- 用户反馈"部署很慢"的答案：慢的是从源码构建（首次拉 bun/golang/debian 基础镜像 + bun install + rsbuild + go mod download + go build，5-20 分钟），
  与 `--clean` 无关（image prune -f 不删 build cache，只删悬空镜像）。想恢复秒级部署要在本地/CI 构建后推自己的 registry，服务器只 pull。
  想加 BuildKit cache mount 加速需要改 Dockerfile，**未擅自改**，需先确认服务器 `docker buildx version`。
